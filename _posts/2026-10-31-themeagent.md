在华为实习期间，我参与了 **ThemeAgent** 的核心开发。它是面向 HarmonyOS 主题开发场景的 IntelliJ 插件，围绕主题配置的检查与修复，把大模型、证据检索和 IDE 中的操作串联起来。

这篇文章由我的原个人主页整理而来，记录公开可讨论的工程思路。文章日期是本次整理发布的日期，实习开始于 2026 年 6 月。这里不展开内部源码、实际业务配置或内部设计文档，也不把特定任务集上的实验结果当作普适结论。

## 从修复建议到工程动作

模型可以给出一个看起来合理的修复建议，但在 IDE 中真正改动文件，还需要回答几个问题：建议依据什么、是否处于允许的范围、谁来批准，以及失败后如何恢复。

ThemeAgent 的工作链路围绕这些问题展开：

1. **理解任务边界**：确定输入、文件范围与当前阶段。
2. **检索证据**：结合配置结构与关联信息定位问题，记录证据来源和缺口。
3. **提出修复**：生成可阅读的差异，让修改意图可供检查。
4. **审批与写回**：人工确认之后，再执行写入。
5. **验证与恢复**：检查写入结果；出现异常时，利用检查点与显式回滚恢复状态。

这里最重要的区分是：**模型提出动作，系统决定动作是否可以执行。**

## 把线性流程整理成 Agent Runtime

我的一部分工作，是把线性执行流程重构为配置驱动的 Agent Runtime。不同场景可以有不同的配置和能力范围，但工具调度、状态提交与风险判断需要遵循一致的执行方式。

运行时采用 ReAct 工具循环，把当前任务状态交给规划过程，再对提出的动作做校验。校验覆盖阶段、权限、预算与风险；越界动作不应进入工具执行。

对于可以独立完成的只读任务，可以采用有界并发。写操作则需要明确的先后关系和审批边界。并发能力与执行权限是两件事：能够同时发出多个工具调用，并不意味着这些调用都有权修改内容。

实现中使用了 Java 17、IntelliJ Platform SDK 与 JCEF / React，分别承接插件能力、IDE 集成与交互界面。Agent Profile 与 Skill Host 用于收敛不同场景的配置差异。

## 让检索围绕证据缺口展开

在定位问题时，检索的目的不是尽可能多地收集文本，而是回答当前诊断中尚未解决的问题。

ThemeAgent 的证据检索涉及 GraphRAG 与 Neo4j。我关注的是如何把已知线索、待探索的关联、已有证据和剩余缺口组织成可追踪的状态。这样，下一步检索可以围绕缺口展开，而不是不断向上下文追加材料。

这种组织方式也让终止条件更明确：已有证据是否足以支持判断，仍然缺少什么，以及继续搜索是否值得。证据本身和证据来源都应该能够回到诊断过程里。

## 把写回做成可检查的闭环

写回是整个链路中需要格外清楚的边界。修复预览、人工批准、实际写入和结果校验是不同阶段，不应混成一次不可见的动作。

| 阶段 | 需要保留的信息 |
| --- | --- |
| 预览 | 修改前后的差异，以及修复依据 |
| 审批 | 本次允许执行的操作范围 |
| 写回 | 实际执行结果与任务状态 |
| 校验 | 修改是否满足预期，是否需要恢复 |
| 恢复 | 检查点与显式回滚路径 |

这部分工作也涉及长任务中的上下文治理。对话摘要可以帮助模型继续理解任务，但恢复不能只依赖一段自然语言总结；关键执行状态、证据与检查点需要被系统明确保存。

## 这段实践带来的思考

对我来说，开发 Agent 不只是把工具交给模型。更具体的工作，是定义工具能做什么、在什么条件下可以执行，以及执行之后怎样确认结果。

ThemeAgent 把这些问题放到了同一个工程场景里：运行时承担调度与状态，检索补足证据，界面让人看见差异，审批和恢复约束写入。只有这些环节能够相互衔接，一次模型建议才有机会成为可检查、可恢复的软件操作。
